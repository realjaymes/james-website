A build for PostHog

Flowbackdesk: running the PostHog wizard from the developer's chair

James Praise · Marketing and GTM Operator

Flowbackdesk is a mock product I built for this test. The code is public on GitHub, including the setup report the wizard wrote.

The run

Why I built an app

I wanted to judge the onboarding by using it, so I needed a project the PostHog wizard could work on. My own site is static HTML, and the wizard installs into framework apps. I built Flowbackdesk instead: a three-page Next.js funnel with a landing page, a pricing page and a signup form. The pages follow a real conversion path, so the events would form a funnel worth reading.

What the wizard did

I ran one command from the project root: npx -y @posthog/wizard@latest. Then the wizard did the rest.

  1. It detected the Next.js App Router on its own.
  2. It opened a browser so I could log in to PostHog Cloud and pick a project and region.
  3. It installed posthog-js and created instrumentation-client.ts to start PostHog.
  4. It wrote the project key into .env.local, a file git ignores, so the key never entered the repo.
  5. It added an /ingest reverse proxy in next.config.ts, so events still send when an ad blocker is running.
  6. It turned on autocapture for pageviews and clicks.
  7. It read my components and wrote three custom events and an identify call, without being told where they belonged.

On signup it also called posthog.identify(email). Then it built a starting set in the project: an Analytics basics dashboard, a three-step signup funnel from button click to completed signup, signups over time, a plan breakdown and a homepage button comparison. All of it is listed in the setup report it left in the repo.

I never opened the docs to find where the init call goes. The wizard found the funnel in my code and instrumented it.

What it means

What a developer notices

It's an agent that reads your codeThe wizard runs on AI models through PostHog's own gateway, per its README, so the developer brings no API key. It read the code and decided where tracking belonged. Time to first event was minutes.
Autocapture and named events, togetherAutocapture fills the dashboard on day one, so nobody stares at an empty chart. Named events like signup_completed are what make funnels and retention worth reading. The wizard sets up both.
The proxy is a quiet winRouting events through the app's own /ingest path stops ad blockers from dropping them. Most teams find that problem late. The wizard ships the fix by default.
Identify turns traffic into peopleOne identify call on signup turns an anonymous event stream into a history for each user. Cohorts and lifecycle work start there.

How I'd launch it

Developers trust what they can watch on code that looks like theirs, so the launch would show the wizard working and let the diff speak.

An uncut recording on a real repoRun the wizard on a known open-source Next.js project, start to finish, with no edits. The length is the claim.
The diff in the docsA changelog entry and a docs page that show the exact files the wizard wrote, so a skeptical engineer can check every line before running it.
Seed it where PostHog's launches already landPostHog's own launch guide names what works for it: Hacker News, newsletters, small events and posts from real people. The recording fits all four, posted by the engineer who ran it.
Measure installs that reach an insightCount wizard runs that end with a first insight viewed. Runs started only show that the video got clicked. Runs that reach an insight show the story held up in real projects.

The wizard now has a self-driving mode that also connects GitHub, turns on Session Replay and Error Tracking, and sets up Signals, per the same README. That's the bigger next story. I'd run it on the same kind of app first and write down what happened before saying anything public about it. Each launch gets its own plan, the way PostHog's launch guide describes, so the self-driving launch would be written from that run.
